# Technical decisions

**Go 1.22+ and the standard library.** `net/http` supports the small route set without a framework, `int64` represents cents exactly, and the race detector helps exercise concurrent callers. `database/sql` gives a narrow API for persistence. The module pins `modernc.org/sqlite v1.34.5` because that release supports the Go 1.22 floor; the newest release initially pulled a newer Go requirement.

**One local SQLite database.** It makes a clean checkout runnable without PostgreSQL, Docker, or credentials. WAL lets readers operate alongside a writer. SQLite admits one writer at a time, so each transfer starts `BEGIN IMMEDIATE` before reading balances and keeps the transaction short. `CHECK` constraints reject negative balances, `STRICT` tables prevent non-integer stored amounts, and the unique idempotency key is a durable backstop. Each file-backed store allows up to eight pooled connections, with foreign keys and busy timeout configured on each connection; `:memory:` stays on one connection so it remains one database. This improves simultaneous reads while writes still serialize through SQLite.

**No SQLite row-lock claim.** `SELECT ... FOR UPDATE` is not valid SQLite syntax; sorting account IDs cannot create SQLite row locks. A future PostgreSQL implementation would lock both account rows in ascending ID order to avoid AB–BA deadlocks, then use the same conditional debit and transaction boundary.

**Balance plus immutable transfer entries.** The current balance is stored for fast reads. Opening funds are recorded as `initial_balance_cents`; every successful transfer creates a negative sender entry and a positive receiver entry. The entry pair, account mutations, transfer record, and idempotency key share one transaction. The seeded audit reconstructs each account and checks global conservation and zero-sum entry pairs. The database does not itself enforce that a transfer has exactly two entries; transaction code and tests do.

**Idempotency contract.** A successful transfer owns its key indefinitely. Replays with the same source, destination, and amount return the original transfer ID, even if the source can no longer afford it. Reusing a key with different fields returns a conflict. Rejected attempts do not reserve keys. Comparing the three stored fields directly is simpler than introducing a payload hash. A commit error could leave the client unsure whether the commit took effect; it should retry with the same key to resolve the outcome.

**Boundaries and limits.** JSON is decoded directly into `int64`, with unknown fields, trailing data, oversized bodies, and imprecise amount representations rejected. The service has no auth and supports arbitrary funded account opening because the assignment asks for it; bind it to localhost for demonstration. History has no pagination and idempotency keys have no expiry. These would need policies and tests in a production service. PostgreSQL becomes attractive when more than one writer, multiple service nodes, or operational reconciliation is required.
